# 产品 PRD MVP

将已确认的业务判断转译为开发可执行、可验收的 PRD。采用「业务判断在前，页面说明居中，数据与规则兜底」的写法。参考成熟 PRD 的章节层级和字段粒度，而不是只输出功能概览。

## 反向 PRD：以现有产品为事实源

当用户要求为已经实现、反复迭代的项目补写 PRD 时，按以下优先级取证：当前可达路由和页面 → 状态模型、表单默认值与校验 → 组件交互 → 历史 PRD／README。不要将遗留代码、无入口页面或历史文档自动写入当前范围。

先输出并经用户确认信息架构；发现“代码有页面但当前导航隐藏”这类会改变范围的差异时，必须询问。其余通用交互可依据实现直接定义；无法从实现判断且会影响业务结果的规则标注「待确认」。

对每个可达页面逐项盘点：页面入口、视觉区块、字段、默认值、可见条件、点击行为、保存时机、状态、失败反馈、跳转和关联数据。不能只根据模块名称概括功能。

## 工作原则

- 将产品 Demo 视为需求澄清和高保真验证手段。Demo 与 PRD 一起交付开发：Demo 表达页面视觉、布局、控件形态与可见交互；PRD 表达功能定义、字段定义、业务逻辑、状态、校验和验收。
- 使用真实开发 PRD 的产品语言：描述用户、业务对象、页面、字段、状态、规则和验收；禁止在正文出现“Demo”“演示”“mock”“localStorage”“前端临时实现”等过程或实现词。
- 如需记录事实来源、当前实现差异或技术约束，将其放入文档信息、待确认事项或独立研发说明，不混入产品需求。
- 先确认用户问题、MVP 目标和本期不做事项；不要从页面或组件开始写。
- 以用户任务组织功能，而非按技术组件罗列需求。
- 每条需求说明触发条件、系统行为和结果；不要留下“支持”“优化”“适配”等不可验收表述。
- 未提供的业务规则标记为「待确认」，不要用常识补写为既定事实。
- 只写本期需要实现和验证的内容；后续设想放入「迭代假设」，不得混入验收范围。

## 写作流程

### 1．整理输入，先做范围判断

从用户提供的材料中提炼以下内容。缺失且会改变产品范围时，先提出一个最关键的问题；其余信息可标为待确认。

| 输入 | 要回答的问题 |
|---|---|
| 用户与场景 | 谁在什么情况下遇到什么问题？ |
| 现有方案 | 用户当前如何解决，哪里不足？ |
| 产品定位 | 产品是什么，不是什么？ |
| MVP 目标 | 本期要验证的核心假设或完成的核心任务是什么？ |
| 边界 | 本期明确不做什么，为什么？ |
| 资源与约束 | 渠道、已有内容、数据、平台、合规和技术限制是什么？ |

先输出一句话问题定义：

> 为【目标用户】在【场景】中解决【具体问题】，通过【最小能力】达成【可验证结果】。

### 2．建立信息架构和用户闭环

先列模块，再列页面，最后列页面之间的跳转。每个模块只服务一个主要用户任务。

```text
入口页
├─ 列表／发现
│  └─ 详情
└─ 我的／管理
```

为每个核心任务写出闭环：进入 → 输入／选择 → 校验 → 提交或操作 → 结果反馈 → 去向。优先保证一个最小闭环，不提前加入交易、社交、复杂权限或自动化等重能力。

### 3．按页面写功能需求

使用 `assets/prd-template.md` 的页面模板。每个页面必须包含：

1. 页面目标与入口；
2. 页面区块和信息层级；
3. 字段、展示规则与默认值；
4. 用户操作、触发条件、系统行为、完成结果；
5. 加载、空、失败、权限和校验状态。

对复杂页面，必须额外写出：

- 不用 ASCII 重复 Demo 已清楚呈现的页面结构；仅在没有 Demo 或页面关系无法从 Demo 判断时补充结构说明；
- 顶部操作区的每个字段、状态和按钮定义；
- 每个开关、单选、标签和视觉状态的业务含义与默认值；
- 条件显示／隐藏、禁止操作、二次确认、自动保存与数据同步规则；
- 列表卡片上的徽标、圆点、颜色、状态文案分别代表什么，何时出现或消失。

将“有一个按钮”改写为可执行规则，例如：

> 用户点击「收藏」后，未登录则进入登录流程；登录成功后返回当前详情页并完成收藏。已收藏时按钮显示「已收藏」，再次点击取消收藏并刷新收藏数量。

### 4．补齐流程、权限和数据

- 将跨页面操作写入「关键业务流程」；不要在多个页面章节重复叙述。
- 明确角色、可见范围、编辑权限和不可逆操作的二次确认。
- 按业务实体而非页面定义数据模型。每个字段必须能追溯至页面展示、用户输入、筛选、计算或权限规则。
- 对枚举、状态流转、排序、时间和删除规则写出明确值或待确认项。

### 5．写验收标准

验收项必须可观察、可判断。至少覆盖：核心闭环、字段校验、权限、空态、失败态、重复提交和数据一致性。

避免「页面正常」「体验良好」；改为「未填写名称提交时，名称字段下显示错误提示，且不创建记录」。

## 推荐目录

按需求规模裁剪，不要为完整而完整：

```text
0．文档信息
1．项目概述
   1.1 背景与问题
   1.2 目标用户
   1.3 产品定位、目标与范围
2．产品架构
   2.1 模块说明
   2.2 页面层级与核心路径
3．功能需求详述
   3.X 模块／页面
4．关键业务流程与权限规则
5．数据模型与字段定义
6．通用交互、异常与边界
7．验收标准与迭代假设
```

小需求可合并第 4 至 6 章；涉及账户、后台、多角色或复杂实体时保留拆分。

## 输出要求

- 先给出「范围判断」：目标、核心假设、MVP 包含项、不包含项和待确认事项。
- 再输出正式 PRD，沿用用户提供的章节、术语与已有文档风格；没有既有格式时使用本 Skill 的推荐目录。
- 表格优先用于字段、操作、权限、状态和验收；叙述优先用于背景、取舍和流程意图。
- 在文末列出「待确认事项」和「迭代假设」，不要将其伪装成本期结论。
- 功能需求详述采用“页面结构 → 字段定义 → 默认值 → 交互逻辑 → 状态与校验”的固定顺序；不要只用一张模块级摘要表替代页面规格。
- 从现有项目反推 PRD 时，先在文档开头写明事实源、当前用户可达范围和明确排除项。

## 自检

- 每个功能是否能追溯到一个用户问题或 MVP 假设？
- 是否明确了本期不做的高复杂度能力？
- 每个操作是否写明条件、行为和结果？
- 每个表单是否写明必填、格式、默认值和失败反馈？
- 每个列表是否具备加载、空和失败状态？
- 每个字段是否有明确用途和归属？
- 每条验收标准是否可以被独立验证？
- 每个可达页面的顶部、卡片、字段、默认值和可见状态是否都有定义？
- 是否已把代码中的展示状态转译成业务含义，而非只描述样式？
